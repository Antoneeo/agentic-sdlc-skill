## Use Cases / User Needs
- **UC1 — the normal user updating the package.** Runs `npm i -g` (or first install). From then on, every project on the machine with a docs root gets session orientation automatically; projects without one see nothing (`orient` is fail-open, exit 0, pinned by tests). No question was ever asked; one printed line tells them what happened and how to opt out.
- **UC2 — the user who removed the hook on purpose.** They deleted the entry from `~/.claude/settings.json`. No later install or update ever re-adds it — removal is a standing opt-out, recorded by a marker.
- **UC3 — the user uninstalling the package.** `npm uninstall -g` removes the skill files; the global hook naming the now-missing validator would be a manufactured wired-and-DEAD state (F-041's "worst of the three"). Uninstall surgically removes the family's global hook entry and clears the marker, so a future reinstall wires afresh.
- **UC4 — the agent reading the residual check note.** On machines the installer never touched, the note still fires — now written consequence-first ("sessions start unoriented…"), naming the one-command fix, so the agent's relayed question is answerable by a human.

Product-name buckets: `~/.claude/settings.json` EXISTS (Claude Code user settings; hooks at user level are the client's documented feature), `postinstall.js`/`preuninstall.js`/`init.js`/`lib.js` EXIST (the npm lifecycle scripts), `wireOrientHook` EXISTS (`lib.js:325`), `orientSettingsState`/`findOrientHook`/`orientHookValidator` EXIST, `test_clients.js` EXISTS (node:test battery, stubbed-HOME harness), `~/.agentic-sdlc/` EXISTS (the family's agent-global root, SKILL.md §Agent-global KB), **`wireGlobalOrientHook` NEW**, **the wired-once marker NEW** (`~/.agentic-sdlc/orient-hook-wired`), `check` notes EXIST (F-041). ## Functional Spec
Trigger fires: new install-time behavior + changed note wording.

**FS-1 — global wiring at install (Claude Code only).**
1. `postinstall.js`, after successfully installing the skill for the `claude` client, calls `wireGlobalOrientHook`. Target: exactly ONE file, `client.home/settings.json` (user level has no `settings.local.json` split — the path is machine-local by nature and never committed).
2. Wire only when ALL hold: python detected (the `init.js` candidates loop, moved to `lib.js` as shared `detectPython()`); the installed validator exists at `skillTarget(client)/scripts/<entry point>`; the path passes `ORIENT_UNSAFE_IN_PATH`; the settings file parses into a recognized shape (`orientSettingsState` reused verbatim — unrecognized ⇒ write nothing, code `malformed`); no family orient hook already present (`findOrientHook` — matches ANY family entry point, which IS the multi-lens dedup: first installed lens wins); no marker line exists for the CURRENT target path.
3. **The marker (`<kb-root>/orient-hook-wired`, where `<kb-root>` is the family's agent-global root — the `DEFAULT_KB_ROOT` constant `~/.agentic-sdlc`, honoring the existing `AGENTIC_SDLC_KB_ROOT` seam so tests isolate it for free)** records "wired once on this machine", one line per wired settings TARGET PATH (the CLAUDE_CONFIG_DIR problem: settings are keyed on `client.home`, a plain boolean marker on `homedir()` — the two can disagree; recording the target path scopes the opt-out to the file that was actually wired). Hook absent + current target listed in the marker ⇒ code `opted-out`, write nothing — UC2's standing opt-out. Current target NOT listed (e.g. a fresh `CLAUDE_CONFIG_DIR`) ⇒ wire and append its line. Marker is also written on `already` (a hand-wired hook, once removed, is respected the same way). Marker write is fail-open (a failed write does not undo the wiring; the code still reports `wired`).
4. Existing-hook semantics mirror the project writer: resolves → `already`; names a validator that does not resolve → `broken` (report with the corrected command, never rewrite); no token names a validator → `unverifiable` (never touched).
5. The hook entry pushed is the documented grouped shape with `timeout` and a lens-neutral `statusMessage` ("Loading docs orientation..."), command = `<python> "<absolute validator>" orient` — **no `--hybrid`** (a machine-global hook cannot know per-project mode; on a Hybrid project the spine orientation still emits and only the devPNT pointer line is absent — declared degradation, ENFORCEMENT documents it).
6. Codes: `wired | already | opted-out | broken | unverifiable | malformed | no-validator | no-python | unsafe-path | write-failed` — result codes, caller owns wording (the `wireOrientHook` contract, reused).
7. `postinstall` prints ONE user-language line per outcome; `wired` names the file and the opt-out ("remove that entry — it will not be re-added"); `already`/`opted-out` print nothing (noise rule); `broken` prints the correction.
8. Acceptance: fresh HOME → wired + marker created + settings carry exactly one SessionStart entry; second run → `already`, file byte-unchanged and the marker still carrying exactly ONE line for the target (append is idempotent — one line per target, never duplicated by the `already` path); hook removed by hand, target listed in the marker → `opted-out`, file untouched; sibling lens's hook present → `already` (no second entry); malformed settings → `malformed`, file untouched; no python → `no-python`, nothing written.

**FS-2 — project-level `init` becomes global-aware.**
`wireOrientHook` (project writer) gains a user-settings check placed **AFTER its existing two-layer project scan, immediately before the write**: a project-level `already`/`broken`/`malformed`/`unverifiable` is reported FIRST (a check that preceded the scan would mask a dead project hook behind "covered globally" — F-041's worst state, silently re-manufactured); only a project with no hook of its own gets `global` when the user settings carry a RESOLVING family hook. A user-level entry whose validator token is not absolute is `unverifiable` (there is no cwd to resolve against at user level). Non-resolving user-level states are enumerated, consistent with the FS-1.4 doctrine: a DEAD global hook ⇒ proceed with the project write AND print the broken-global correction line (a dead wrapper must not leave the project unoriented); an UNVERIFIABLE global entry ⇒ proceed with the project write, with an info line naming the user file. `init` prints "covered by the machine-global hook" on `global`, and its result-code switch gains a **default arm** (an unknown code prints the manual pointer instead of silently skipping — a lens port missing a case must be loud). Prevents new double-orientation states; pre-existing doubles are documented (ENFORCEMENT: "orientation printed twice ⇒ remove one of the two entries").

**FS-3 — uninstall symmetry.**
`preuninstall.js`, before removing skill dirs: parse EVERY settings target the marker lists, unioned with the current `client.home/settings.json` (the marker remembers each wired world, so a hook wired under `CLAUDE_CONFIG_DIR=/x` is cleaned even when the uninstall shell lacks that env — without the union, that world keeps a hook whose validator is being deleted: the manufactured dead state, undetected until that world's own `check`); same recognized-shape rule per file; remove ONLY SessionStart entries whose validator token resolves INTO a skill target being removed — containment judged by ONE normalized-comparison helper shared by containment AND the marker-line lookup, built on the PLATFORM'S OWN `path.relative` (win32 folds case and separators; an unconditional `path.win32` on POSIX would case-fold genuinely distinct paths — T3a's false positive). A naive prefix match misses `c:\users` vs `C:\Users` and MISSES the removal, re-manufacturing the dead hook — the false NEGATIVE, T3b; the same case-variance on the MARKER lookup would read a listed target as "not listed" and re-wire against a standing opt-out, so the helper guards both lookups. The case-variant test row drives `path.win32` explicitly so it runs on every platform. An emptied group / emptied `SessionStart` array is pruned so the file is left clean. **The marker line for that target is cleared ONLY when an entry was actually removed** — when no attributable hook was present (the user had removed it: UC2), the marker STAYS, so the opt-out survives uninstall/reinstall and survives a SIBLING lens's uninstall (the B2 state walk: mkt's preuninstall finding no hook must not erase kb's opt-out memory). Deleting the marker file by hand is the documented re-enable gesture. Fail-open: unreadable/unrecognized settings ⇒ remove nothing, print the manual pointer, never abort npm. Result: no manufactured dead hook (UC3); healthy-path uninstall+reinstall wires afresh (hook was present ⇒ removed ⇒ marker line cleared); sibling self-healing preserved for the same reason.

**FS-4 — the residual check note: user language AND global-aware (spine ×3).**
The B1 defect, fixed at the root: after FS-1, a wired machine's projects are deliberately project-level-unwired (FS-2), so a detection that scans only project files would print the unwired note FOREVER on exactly the machines this unit fixes. Therefore:
1. `orient_hook_state` additionally scans the USER-level settings file — `$CLAUDE_CONFIG_DIR/settings.json` when set, else `~/.claude/settings.json` — with the same predicate, shapes, caps and fail-open rules; the any-resolves aggregation runs across project AND user entries (a resolving hook at either level ⇒ silent; dead-at-both-levels ⇒ dead note). A new isolation seam — env `AGENTIC_SDLC_USER_SETTINGS` — overrides the user-settings path. **Read at CALL time inside the detection, a DECLARED divergence from `AGENTIC_SDLC_KB_ROOT`'s import-time read (`sdlc_core.py:74`)**: `unittest discover` imports the module once before any test runs, so an import-time seam would be frozen before the matrix could set it (the KB_ROOT pattern names the env var convention, not the read moment). The `$CLAUDE_CONFIG_DIR || ~/.claude` fallback is read at call time too, and one in-process row pins the real `CLAUDE_CONFIG_DIR` derivation. The user-settings path derivation joins the DECLARED python↔JS mirror list in the spine comment (beside the entry-point names) — both sides compute `CLAUDE_CONFIG_DIR || <home>/.claude`, and empty-string env is falsy on both sides. It so the in-process test matrix and the SUBPROCESS golden runs stay deterministic on a dev machine that has a real global hook (without the seam, the goldens differ per machine: nondeterminism by construction).
2. Both note texts rewritten consequence-first, honest on non-Claude machines (the spine is client-agnostic — "it wires the hook for every project" would overclaim on Codex-only, no-python and opted-out machines):
- unwired: `[note] agent sessions start without automatic orientation on this machine (no session-orientation hook found at project or user level). Fix once: update or reinstall the skill npm package (on Claude Code with Python it wires the hook machine-wide), or wire it per ENFORCEMENT.md par.4`
- dead: `[note] a session-orientation hook is configured but points at a validator that no longer exists, so sessions start unoriented. Fix: update or reinstall the skill npm package, or correct the command. Details: ENFORCEMENT.md par.4`
(The two fragments stay disjoint: "without automatic orientation" / "no longer exists".) Declared residual: on an OPTED-OUT machine the reinstall advice wires nothing by this unit's own design — the par.4 pointer (marker deletion = re-enable) closes that loop one hop away; the note text does not grow a third clause for it (noise rule).
Acceptance: the F-041 matrix passes with the new fragments PLUS new rows — global hook wired (via the seam) ⇒ silent; global dead + no project hook ⇒ dead note; global dead + project live ⇒ silent; seam pointing at a nonexistent path ⇒ behaves as no user file. The golden runners (×3) export the seam to a fixture-local path in their subprocess env; baselines regenerate ×3.

## Security & Threat Model
- **T1 — writing user-level config from a lifecycle script.** Highest-trust surface in the unit. Mitigations, inherited from the project writer and preserved: recognized-shape-or-write-nothing (`orientSettingsState`); the command is built from installer-known paths — `os.homedir()` OR the user's own `CLAUDE_CONFIG_DIR` (`lib.js:75`, which genuinely relocates the settings; env-derived, so NOT "homedir-only") — every candidate filtered by `ORIENT_UNSAFE_IN_PATH` before use; JSON serialization only, no shell; one key path touched (`hooks.SessionStart` append), everything else preserved via parse/serialize of the recognized shape.
- **T2 — the marker as a footgun.** Two directions: a stale marker suppressing wiring forever (→ FS-3 clears the target's line when a hook was actually removed; hand-deleting the marker is the documented re-enable), and a cleared marker erasing a standing opt-out (→ the B2 fix: never cleared when no hook was removed). Marker read/write fail-open both ways; keyed per settings TARGET PATH so a `CLAUDE_CONFIG_DIR` world never inherits another target's opt-out silently.
- **T3 — uninstall touching the wrong hook (both directions).** (a) False positive — deleting someone else's entry: attribution is strict (validator token resolves into a removed skill target; unverifiable/foreign ⇒ untouched). (b) **T3b, false negative — MISSING the removal** re-manufactures the dead hook UC3 exists to prevent: containment is `path.relative`-based with win32 semantics (case-insensitive, separator-normalized), never a naive string prefix; a case-variant test row pins it.
- **T4 — double orientation (noise).** New doubles prevented by FS-2; legacy doubles documented with the remedy. The global hook on non-docs projects is silent by the fail-open orient contract (pinned by existing tests).
- **T5 — a failing new step breaking npm install/uninstall.** Every new path wrapped; lifecycle exit codes unaffected (npm treats postinstall failure as install failure — unacceptable for an optional convenience).
- **Eliminated by construction:** the incomprehensible user question (the wiring happens inside the user's own act); the manufactured dead hook at uninstall (FS-3).
