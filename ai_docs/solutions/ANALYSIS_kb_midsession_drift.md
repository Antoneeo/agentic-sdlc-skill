## Functional Spec
Trigger fires: both items add observable behavior.

**FS-A — the wiring note in `check`.**
1. Immediately after the spine's `check` summary line (so, in kb, BEFORE the overlay's graph/corpus sections — the position the goldens freeze), when no session-orientation hook is detectable under the project root, print exactly ONE informational line naming the files searched and pointing at ENFORCEMENT §4 / `init`.
2. A hook counts as wired when a SessionStart-shaped entry in `.claude/settings.json`, `.claude/settings.local.json`, or `.codex/hooks.json` carries a command that names a known validator entry point (`sdlc_check.py` or `mkt_check.py`) and invokes ` orient` (same predicate as `lib.js findOrientHook`, both shapes: grouped `{hooks:[...]}` and direct hook objects, the `/ orient(\s|$)/` regex semantics).
3. **The dead-hook state is detected, not silently blessed.** When a matching entry IS found, the validator token it names (mirroring `lib.js orientHookValidator`: quoted or bare, the token ending in a known entry-point name) is resolved against the filesystem — relative tokens against the project root. Token resolves → silent. Token does not resolve → a DISTINCT one-line note: hook wired but its validator does not resolve (ENFORCEMENT §4 names this "the worst of the three states": it emits nothing every session AND looks installed — `lib.js` already detects it at init; `check` is where it must surface in-project). No token names a validator → silent (the lib.js contract: "cannot tell" is never reported as broken). **Aggregation across multiple matching entries/files:** silent if ANY matching entry anywhere resolves; the dead note fires only when at least one match exists and NONE resolves (the double-hook state is real — `lib.js:207-211`'s historical double-append hole — and the client runs ALL SessionStart hooks, so a live entry beside a dead one means sessions ARE oriented; a first-match-and-stop mirror of init's flow would nag falsely at every closure).
4. The notes NEVER change the exit code and are NOT `validate` warnings: `validate` (the documented CI path, incl. `--strict`) never prints them and never fails on them. Verified implementable: strict escalation reads only `cmd_validate`'s own warnings list (`sdlc_core.py:1485-1487`); a line printed at the `check` layer after the summary (`:1654-1656`) cannot enter those counters. Rationale for keeping CI out: the wired hook typically lives in git-ignored `settings.local.json`, so CI legitimately cannot see it — a warning there would be a permanent false alarm; on a teammate's fresh clone the note is a true positive (each machine runs `init` once, per §4's table).
5. Detection is fail-open: an unreadable, oversized (cap ~1MB), malformed or directory-shaped settings path counts as "no hook found there" and never crashes or blocks `check`. Reads are `utf-8-sig` (a PowerShell/Notepad BOM'd `settings.json` must not read as unwired — the codebase's own lesson at `sdlc_core.py:1667`; declared divergence from Node, whose `JSON.parse` chokes on BOM).
6. Acceptance: fixture with no client config → note printed, rc unchanged; hook wired in any of the three files, either JSON shape → silent; wired with a BOM'd settings file → silent; wired but validator token does not resolve → the dead-hook note, rc unchanged; malformed JSON → note, rc unchanged; `validate --strict` on the same tree → no note, no new warning; wired via vendored validator path (`tools/sdlc_check.py`, file present) → silent (predicate matches the entry-point NAME, not the path).

**FS-B — the `remind` subcommand (kb only).**
1. `sdlc_check.py remind` prints exactly one line — the kb minimum, self-contained (the distill lesson: it says WHAT TO DO, it never says "follow the doctrine"): triage first with the four levels named; entering a topic the KB may cover → read the topic index (**with its static location anchored in the line: `topics/INDEX.md` under the docs root** — a compacted-context agent, UC2's own scenario, has no other referent) and cite claim ids or state no coverage; decisions made today are recorded at session close.
2. Constant output: byte-identical on every invocation, independent of cwd, `--root`, or repo state; zero filesystem reads; ≤ 500 chars; no skill-internal jargon (the distill payload battery's rule, same term blacklist idea).
3. Exit 0 always; unknown extra argv ignored (a hook must never break a prompt — fail-open like orient).
4. NOT wired by `init`, not now not later by default: ENFORCEMENT documents the manual snippet and the cost (~50 tokens/prompt), the project chooses.
5. Acceptance: one line, byte-stable across two invocations with different garbage argv/roots, length cap, exit 0, term blacklist clean.

## Security & Threat Model
- **T1 — parsing repo-controlled JSON (external input; never L1).** The detector READS `.claude/settings*.json` / `.codex/hooks.json`: `json.loads` inside try/except, size-capped, nothing is executed, nothing is written; the one content-derived value -- the validator token FS-A.3 extracts -- is EXISTENCE-PROBED only, never read, executed, or echoed into output (both notes are constant strings). Residual: on Windows a content-derived UNC token makes the existence probe touch SMB -- metadata-only, accepted (writing stays in JS with its existing `ORIENT_SAFE_SEGMENT`/`ORIENT_UNSAFE_IN_PATH` guards). Malformed input degrades to "not found". Mitigated by construction.
- **T2 — `remind` as an injection channel.** The line enters the agent's context every prompt. It is a versioned CONSTANT in the skill's own code — zero reads means no repo-controlled text can ride it. Eliminated by construction (the zero-read rule is also a test).
- **T3 — false-positive nagging (trust erosion — the distill noise lesson).** Mitigated: detection covers both known client-config locations and both JSON shapes, reads `utf-8-sig` (BOM), and blesses a found-but-unverifiable command (no resolvable token ≠ broken). Accepted residuals, documented in ENFORCEMENT: (a) a Gemini-only project (no hook mechanism) keeps the note — factually true (its sessions DO start unoriented; §4 already documents the manual fallback); (b) a `.codex/hooks.json` wired in a shape other than the §4-documented one yields a false note — the codex shape is pinned by no fixture (§4's own admission), so the matcher covers only the documented shape. The dead-hook note is the inverse trust case: staying SILENT on a wired-but-dead hook would bless "the worst of the three states" — detecting it is part of this threat's mitigation, not a new surface.
- **T4 — a hook that breaks the session.** `remind` exits 0 always, tolerates garbage argv; detection failure can never fail `check`. Fail-open on both surfaces, tested.
